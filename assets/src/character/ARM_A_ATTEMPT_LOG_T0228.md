## Bookkeeping note: attempt-slot 1 was corrected before its first real evaluation

The very first ComfyUI submission (seed 31415, the original "medical/anatomical skeleton" pose prompt, with the pose skeleton itself SDXL-sampled and tiled via `ImageStitch`) returned in ~4s because ComfyUI served it from its own execution cache (T-0218 had already run graphs with matching node inputs) and produced an unusable abstract pattern -- no recognisable skeleton, so no real pose signal reached ControlNet, and the main generation fell back to a multi-figure concept-sheet layout (T-0218's diagnosed "wrong_subject" failure). This was caught and fixed (pose prompt rewritten) before the result was logged as a completed, evaluated attempt, and the corrected run was resubmitted under the same attempt-1 slot, overwriting the cached run's output on disk. Both submissions are disclosed here for a complete record; only the second (below) is counted against the 8-attempt cap, since the first was superseded before evaluation, the same way a bug caught in a test harness before the first real run doesn't count as a used attempt.

## Bookkeeping note: descent-chain background bug affected the first offline measurement

Attempts 1-5 were originally measured (online, right after generation) with a descent chain that had no way to force each cell's actual generated background onto `background_index=0` -- it only trusted Oklab-nearest quantization to land there naturally. It usually didn't (attempt 1's background covered ~0.1% of its sheet in index 0), so nearly every pixel read as "foreground" and the frame-silhouette-delta ratio came out trivially ~0 regardless of real content -- attempt 1 briefly appeared to pass this way despite being a visually obvious wrong-subject failure. `force_cell_corner_background` and `enforce_cell_margin` were added to the descent chain to fix this (flood-fill each cell's own corner-connected background region onto index 0, then clip a small margin at every cell edge), and attempts 1-5 were recomputed offline from their already-generated `sheet_144_raw.png` (no new GPU generation, same pixels, corrected measurement). ## Reading for §23-g

Arm A -- the current documented pipeline (`13-asset-pipeline.md` §3.5), now fully equipped with the style LoRA, IP-Adapter, and OpenPose ControlNet -- does *not* work within an 8-attempt budget, and fails in the same specific way T-0218's under-equipped spike already predicted: co-generating all 9 idle-sheet cells in one pass lets equipment/costume identity drift across rows, even with a clean, deterministic, correctly-formatted pose signal driving every cell to the same pose. Two structural fixes (deterministic procedural pose skeleton instead of an SDXL-sampled one; a "contact sheet" prompt framing instead of "sprite sheet") were necessary just to get the *grid layout and per-cell figure count* right (attempts 1-4), before cross-row identity drift became the visible, dominant failure mode (attempts 5-8) -- suggesting that even substantially more attempts within the same architecture would likely encounter the same drift ceiling, not resolve it by chance.

Attempt 8 promoted to `assets/final/character/player_idle_sheet_arm_a_T0228.png` as the best-effort candidate after the DL-21 8-attempt cap was exhausted without a mechanical criterion-2 pass -- a criterion-3 failure, delivered for §23-g's criterion-1 inspection, not as a passing sheet.
