## Context

**Fresh-ID reissue of T-0048.** T-0048 was a reused cut ID (the
secret-drops `/v1/roll` card, cut in `PLAN.md` v3) — per T-0013
(`docs/PLAN.md`, the gap-tolerant, no-reuse ID allocator), a cut ID must
not be recycled for new scope, so this spawner work is carded fresh here
rather than continuing to live under T-0048.

Rescoped now that `docs/design/07-items-economy.md` has landed,
confirming the supersession flagged during initial GDD reconciliation.
The original scope was a client-invoked `/v1/roll` weighted RNG draw
against `secret_drops`/`drop_grants` (Phase-0 stub data model) — that
model is gone. There is no roll endpoint and no client-triggered "find a
drop" moment; per `docs/design/07-items-economy.md` Section 4, the source
side of the economy is **spontaneous world spawn**, a purely
server-internal process, confirmed and finalized in
`docs/design/03-net-protocol.md` Section 5.

This task builds that spawner: a background process that creates new
`item_instance` rows to keep each `type_id` between a floor and a hard
cap (`07-items-economy.md` Section 2, D-7):

| Tier | Cap | Scales with `P`? |
|---|---|---|
| Common | `k_c · P` | yes |
| Rare | `k_r · P`, `k_r ≪ k_c` | yes |
| Unique | fixed small absolute count | **no** |

Spawned instances land at a world anchor `(archetype_id, anchor_tag)`,
`holder = NULL`, `custody_depth = 0`. The spawn **rate** model itself
(Poisson per tag per tier vs. tear-driven seeding) is open (**E-7**,
`docs/design/OPEN-QUESTIONS.md`) and blocks the *tuning* of this spawner,
not its structure — build the cap-enforcement and floor-topping-up
mechanics now, wire in the real rate model once E-7 is answered. The
economy simulation harness (T-0099) models this same spawner logic
standalone, ahead of and independent from this production
implementation — keep the two in sync rather than letting them diverge
into two different spawn models.

## Story

As the server, I want a background spontaneous item spawner that
enforces per-tier rarity caps — common and rare scaling with population,
unique fixed and population-independent — so that supply stays bounded
and progression-critical types never drain to zero while population is
active.

## Acceptance

- [ ] Spawner creates `item_instance` rows respecting the per-tier cap
      formula above, never exceeding `cap(type, P)` (INV-6)
- [ ] Spawner tops up supply toward a floor for gating-set types, never
      draining a progression-critical type to zero while population is
      active (INV-7)
- [ ] Unique-tier spawning is population-independent — a fixed count,
      never scaled by `k_c`/`k_r`
- [ ] Test: spawner never violates the cap even under rapid population
      growth
- [ ] Rate model itself is a pluggable/configurable component, not
      hardcoded — so landing E-7 later doesn't require re-deriving this
      task's plumbing
