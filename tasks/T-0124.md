## Context

Backlog-review gap: `03-net-protocol.md` currently has no combined
room-entry read. `GET /v1/notes` (§2) fetches notes only, `GET
/v1/items/{id}` (§3) fetches a single item by id — nothing fetches
"everything relevant at this anchor" in one call. This card designs and
implements that endpoint; it's new, not a rename of something existing.

All three data classes it needs to combine are already keyed on the same
`(archetype_id, anchor_tag)` pair in `04-data-model.md`: `item_instance`
(`anchor_arch`/`anchor_tag`, §3), `offering` (`anchor_arch`/`anchor_tag`,
§3), and `notes` (`archetype_id`/`anchor_tag`, §5). That shared key is
what makes a single-transaction combined read possible.

**Depends in prose on T-0123 (run assembler)** — a room-entry snapshot
only makes sense once a run has an assembled archetype/variant to enter.

## Story

As the server, I want one consistent, single-transaction snapshot per
room entry, so that the client sees items hosted by the caller, globally
visible offerings, and global notes at that anchor all as of the same
instant.

## Acceptance

- [ ] `GET /v1/anchors/{archetype}/{tag}` returns three visibility
      classes in one response: (1) `item_instance` rows anchored there
      that the caller can act on, (2) open `offering` rows at that
      anchor (visible to everyone, per `03-net-protocol.md` §4), (3)
      `notes` at that anchor (tag-equality lookup, `03` §2)
- [ ] All three reads happen inside **one database transaction** — this
      is the whole point of the endpoint, not an optimization detail.
      **A torn read is a real bug here**: reading `item_instance` before
      an in-flight `POST /v1/offerings` commits can show an item as
      still loose at the anchor when it is, a moment later, already
      backing an offering — the client would then attempt an action
      against a state that no longer exists server-side
- [ ] Test: concurrent `POST /v1/offerings` against an item at the same
      anchor never produces a snapshot showing that item as both loose
      and offered
- [ ] Broadcast/petition notes (`is_broadcast = true`) are excluded from
      the anchor-scoped notes list — they have no anchor per
      `04-data-model.md` §5 and surface through a different path
      (T-0117)
- [ ] Response shape documented in `03-net-protocol.md` alongside the
      existing route tables (§2-§4) once implemented
