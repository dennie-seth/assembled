## Context

Backlog-review gap: nothing in the current task set assembles a run's
world set from the archetype/variant/room primitives `01-vision.md` §7
and `16-level-design.md` §2 already define.

**Doc conflict worth flagging before implementation:** `01-vision.md` §7
states "a run selects 5-7 archetypes... ~15 rooms visited per run", while
`16-level-design.md` §2 explicitly ties the run's tear budget to "exactly
3 archetypes per run" (one chain tear each on archetypes 1-2, one pocket
tear on archetype 3). This card follows the **16 §2** figure since it's
the more specific, mechanically load-bearing one (tear budget depends on
it directly), but `01` §7 is marked "locked" and disagrees — worth a
design-chat reconciliation, not silently picked around.

Variant selection is population-gated: `variant.unlock_population`
(`04-data-model.md` §2, open question **V-9**, `01-vision.md` §11) is the
threshold that makes a variant eligible for a given universe's population.

Depends on identity/session existing first (T-0093 session lease,
T-0094 identity/token) — a run is assembled for an authenticated identity
with a live lease. Not encoded as a graph edge per current convention
(new cards ship with `depends_on: []`); noted here in prose instead.

## Story

As the server, I want to assemble a run of exactly 3 archetypes (one
eligible variant each), size-aware against an 18-room cap, so that a
player gets a coherent, population-appropriate world set and the server
has a record of what was assembled for later proof-of-play checks.

## Acceptance

- [ ] Assembling a run selects exactly 3 archetypes and exactly one
      variant per archetype
- [ ] Variant selection only considers variants whose
      `unlock_population` threshold the current population satisfies
      (V-9 gating) — an ineligible variant is never assembled
- [ ] The assembled set respects the 18-room cap: room counts across the
      3 chosen variants (each individually in the 5-8 room band,
      `01-vision.md` §7) sum to at most 18
- [ ] The assembled archetype set is recorded (`run_archetypes`,
      `04-data-model.md` §4) so proof-of-play checks (D-12, T-0098) have
      something to query
- [ ] Test: two consecutive assemblies for the same population can
      produce different archetype/variant combinations (selection is not
      hardcoded to one fixed set)
- [ ] Test: a variant below its `unlock_population` threshold is never
      selected regardless of how many times assembly runs
