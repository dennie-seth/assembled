## Context

`15-server-ops.md` §9.2 (Copy-on-Write, Logical layer — uniques only):
**"Unique custody is append-only. Never update a unique's custody in
place."** Affordable specifically because uniques don't scale — a fixed
small absolute count (`07-items-economy.md` §2) keeps the full history
of every unique trivially small, unlike common/rare instances at `k · P`
volume which stay ordinary in-place MVCC rows.

```sql
unique_custody_log(
  unique_id     UUID NOT NULL,
  seq           BIGINT NOT NULL,        -- monotonic per unique_id
  holder        UUID NULL,
  hosted_by     UUID NULL,
  shard_id      SMALLINT NULL,
  lease_expires TIMESTAMPTZ NULL,
  event         SMALLINT NOT NULL,      -- seed|lease|take|use|bleed|release|complete
  at            TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (unique_id, seq)
);
```

What it buys, per `15` §9.2: exact reconstruction of custody at any
instant, duplication detection (two `take` events with no intervening
release makes an INV-2 violation visible instead of inferred), a
post-restore audit query (§5's "every unique exists exactly once"
check), lease forensics for **OPS-2**, and free `custody_depth`
provenance — `count(*)` over the log instead of a separately maintained
counter.

## Story

As the server, I want unique-item custody changes recorded as an
append-only log rather than updated in place, so that custody history is
exactly reconstructible and duplication is detectable after the fact
rather than only inferred.

## Acceptance

- [ ] `unique_custody_log` table matches the schema in `15-server-ops.md`
      §9.2: `(unique_id, seq)` primary key, `seq` monotonic per
      `unique_id`, `event` one of seed/lease/take/use/bleed/release/complete
- [ ] Every custody-affecting operation on a unique instance (seed,
      lease grant/reclaim via `UniqueAuthority` §4, `take`, `use`,
      bleed, escrow release, exit-condition completion) appends a row —
      **no update statement ever touches an existing row in this table**
- [ ] Current custody for a `unique_id` is derived as the latest row by
      `seq`, never stored redundantly elsewhere as the source of truth
- [ ] `custody_depth` for uniques is computed as `count(*)` over the log
      for that `unique_id`, not incremented on `item_instance` the way
      common/rare instances are (`04-data-model.md` §3)
- [ ] Test: two `take` events for the same `unique_id` with no
      intervening `release`/`bleed` row is detectable via a query over
      the log (the duplication-detection property from `15` §9.2)
- [ ] Test: reconstructing a unique's holder at an arbitrary past
      instant from the log alone produces the same answer as the
      contemporaneous state was at that time
