### Root cause

The 59% rework rate (191 FAIL / 323 validations) has two primary root causes,
confirmed from the T-0186 sampled investigation (56% rate, 171 validations)
and the new evidence cards in this window.

**Root cause 1 — missing Acceptance section (T-0137, T-0139, T-0140, T-0141, T-0147, T-0170):**

From T-0186's sample of 16 reworked cards, 6 (37.5%) were caused solely by the
card body having no parseable `## Acceptance` checklist. In every case the
reviewer FAIL note said explicitly:

> "Card T-01xx has no ## Acceptance section — its body is a single user-story
> sentence with no checkable criteria. Per reviewer conventions, a card without
> a parseable Acceptance checklist cannot be verified and is itself a FAIL."

The implementation was fully correct. The rework cycle was: implementer writes
code → reviewer FAILs on missing checklist → implementer adds the section →
reviewer PASSes. This consumed one implementer LLM call + two reviewer LLM
calls (FAIL + PASS) for zero code-quality gain.

### Fix implemented

**Pre-flight check: block implementer runs on cards without an `## Acceptance` checklist.**

Added `tools/board/src/runner/acceptancePreflight.js` — a pure function
`checkAcceptancePreflight(task)` that calls `parseAcceptanceCriteria(task.body)` and
returns `{ok: false, message}` if the result is empty (no section, or section with
prose but no checkboxes). Wired into `RunOrchestrator._runCardInWorktree()` immediately
after any planner expansion and before the first implementer attempt.

Effect: for unassigned (`agent: null`) cards, the planner is still given a chance to add
the Acceptance section — if it fails to, the card is blocked before the implementer runs,
surfacing the authoring gap to a human rather than consuming an implementer+reviewer budget.
For pre-assigned cards, the card must already have a complete spec.

Files changed:
- `tools/board/src/runner/acceptancePreflight.js` (new)
- `tools/board/src/runner/runOrchestrator.js` (import + pre-flight call)
- `tools/board/test/runner/acceptancePreflight.test.js` (new, 9 tests)

### Flow-stats snapshot: why improvement isn't immediately measurable

The pre-flight check prevents future rework for root cause 1 (missing Acceptance
section). However, the 59% aggregate rate is cumulative over 323 validation notes
since project start — it will not drop instantly. The expected effect:

- Future underspecified cards produce 0 FAIL notes (blocked before implementer) instead
  of 1–5 FAIL notes each (implementer + repeated reviewer cycles).
- As new cards flow through and PASS first-try (or are blocked at pre-flight rather than
  at review), the FAIL / (FAIL+PASS) denominator grows with fewer new FAILs, gradually
  lowering the cumulative rate.
- A meaningful signal (rate dropping below 50%) is only visible after 50+ new validations
  complete, which is likely 1–3 weeks of normal throughput at this board's cadence.

  agent sessions so generation can actually run, or (b) clearer guidance in the agent

  Also a separate card.
