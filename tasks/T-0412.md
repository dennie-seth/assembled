## Fix

Two concrete infra fixes, both scoped to the confirmed mechanisms above, both TDD (test committed
before implementation, each its own RED/GREEN commit pair):

1. **`tools/board/src/runner/blockerReport.js`'s `categorizeFailure` now recognizes the `.claude/`
   sensitive-file denials.** `CLAUDE_DIR_DENIAL_REASON` (Edit/Write, T-0374) and
   `CLAUDE_DIR_BASH_DENIAL_REASON` (Bash, T-0411) are both imported from `toolAllowlist.js` and
   checked by literal containment, ahead of the keyword table -- before this fix, a FAIL note
   quoting either denial verbatim matched **no** pattern in `CATEGORY_PATTERNS` (neither contains
   "permission denied", "not allowed", "forbidden", "403", "EACCES", "no grant", "not authorized",
   or "access denied" verbatim) and silently defaulted to `"code-test-bug"`. That default sends a
   card back through the ordinary auto-retry loop -- which can never succeed against a wall no
   code change can clear -- instead of surfacing it as the permission/grant-category blocker it
   actually is, which is what lets `escalationRemediation.js` route it to a human
   (`agent: "dispatch"`) instead of burning retry attempts. This directly targets the mechanism
   behind T-0408's own rework: if a future card hits this exact wall and reports it honestly
   (instead of routing around it the way T-0408 attempt 3 did), it now escalates correctly on the
   first occurrence.
2. **`tools/board/src/runner/claudeDirBashGuard.js`'s `GIT_READ_ONLY_SUBCOMMANDS` now includes
   `commit`.** `git commit` snapshots the already-staged index into a new commit object; nothing
   about its `-m` message text (or an `-F`/`-o` flag) can create or modify a working-tree file
   under `.claude/`, so it belongs in the same read-only-for-this-purpose set as `log`/`diff`/
   `show`/`status`, which were already exempted for exactly this reason. This closes the false
   positive reproduced live above -- a card (any card, not just this one) can now write a commit
   message that discusses a `.claude/` path without being denied for it.

Both changes are unit-tested against the pure functions (`blockerReport.test.js`,
`claudeDirBashGuard.test.js`), mirroring this codebase's established pattern for these two modules.
**Verification constraint:** this session's Bash grant is `git` only (confirmed directly: `npx
vitest run tools/board/test/runner/blockerReport.test.js` required approval and could not be run).
Every new and existing assertion in both touched test files was traced by hand against the updated
logic to confirm the expected pass/fail outcome (traced in detail above for the `git commit`
change, including the three pre-existing tests closest to the new behavior); `cd tools/board && npx
vitest run` itself could not be executed from this session to confirm green mechanically. The
reviewer's own session is the one that can actually execute it.

**Edge cases:**
- [x] A FAIL note that contains the `.claude/` denial text alongside an unrelated keyword match
      (e.g. also mentions "timed out" or "ambiguous"): `categorizeFailure` checks the denial
      strings by containment before the keyword loop runs at all, so the denial wins regardless of
      what else the note says -- same precedence design as the existing host-action-request
      structural check.
- [x] A FAIL note that merely contains the *word* "claude" or a `.claude`-looking path without the
      actual denial sentence: no match -- the check is containment of the full denial string, not
      a loose keyword, so it cannot fire on an unrelated mention.
- [x] `git commit --amend`, `git commit -F <file>`, `git commit -o <path>`: all still read-only for
      this purpose -- none of commit's flags can cause it to create or modify working-tree file
      content, so adding bare `commit` to the subcommand set covers every flag combination, not
      just `-m`.
- [x] A compound command mixing a denied write with a now-allowed `git commit` (e.g.
      `node -e "...writeFileSync('.claude/rules/x.md',...)" && git commit -m '...'`): the write
      segment is still evaluated independently and still denied -- `GIT_READ_ONLY_SUBCOMMANDS`
      only changes how the `git commit` segment itself is judged, never other segments in the same
      compound command.
- [x] `git commit`'s message containing a `.claude/` path is distinguished from `git add
      .claude/x && git commit`: the latter's `git add` segment is a different bareVerb ("add", not
      in `GIT_READ_ONLY_SUBCOMMANDS`) and is still evaluated by the existing fail-closed default --
      this fix only widens what `commit` itself is judged as, not `add` or any other subcommand.
