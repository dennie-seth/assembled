## Fix

Both fixes committed in round 1 are kept -- each is a real, confirmed defect -- but **neither
addresses the measured cause of any of the five Evidence entries above.** They are incidental to
this card's own rework-rate signal, not causal.

1. **`tools/board/src/runner/blockerReport.js`'s `categorizeFailure` recognizes the `.claude/`
   sensitive-file denials (`CLAUDE_DIR_DENIAL_REASON`, `CLAUDE_DIR_BASH_DENIAL_REASON`) by literal
   containment.** This is a real classification gap: before the fix, a FAIL note quoting either
   denial verbatim matched no pattern in `CATEGORY_PATTERNS` and defaulted to `"code-test-bug"`,
   mislabeling the escalation report and remediation card for a card that hit that specific wall.
   **It addresses none of this card's five Evidence entries** -- as shown above, zero of them were
   caused by either denial; it is incidental, not causal. **Round 1's claim that this fix "lets a
   card escalate instead of burning retry attempts" is retracted as false.** `categorizeFailure`
   only ever runs from `buildBlockerReport`, itself only reached from `_escalateIfGenuineBlocker`
   in `runOrchestrator.js` once `stopping` (`isFinalAttempt || noProgress`) is already `true` --
   i.e. after the retry loop has already finished on its own. The fix changes what the escalation
   comment and remediation card *say* about an already-stopped card, never whether, when, or how
   many times it retries, and never which agent it's routed to (`draftRemediationCard` sets
   `agent: "dispatch"` unconditionally for every category -- `escalationRemediation.js`). This
   ordering is now pinned in code, not just asserted in prose:
   `tools/board/test/runner/runOrchestrator.escalation.test.js`'s "exhausts every
   MAX_AUTO_RETRY_ATTEMPTS attempt even when EVERY attempt's FAIL note already carries the
   permission-grant denial text" test, and `tools/board/test/escalationRemediation.test.js`'s
   "assigns agent: dispatch regardless of the blocker category" test.
2. **`tools/board/src/runner/claudeDirBashGuard.js`'s `GIT_READ_ONLY_SUBCOMMANDS` now includes
   `commit`.** This closes a false positive **directly live-reproduced during round 1's own work
   on this card**: drafting a commit message that itself *discussed* a `.claude/` path (exactly
   what this card's own commits naturally need to write) was denied, even though `git commit` only
   snapshots the already-staged index and cannot create or modify a working-tree file under
   `.claude/` no matter what its `-m` text says. A genuine, confirmed defect -- but **incidental to
   the measured rework window** the same way fix 1 is: it was discovered as a side effect of
   writing this very card, not as the explanation for any of T-0396/T-0408/T-0411's FAILs.

**No early-stop is implemented this round -- option (b), the deliberate decision on this card.**
The evidence above shows the denial mechanism caused zero of the five measured failures, so a
first-denial early-stop would optimize for a failure mode with no occurrences in this card's own
sample. The failure direction is also asymmetric: a wasted retry costs attempts, while a
false-positive early-stop abandons recoverable work outright -- and this very card's own round-1
analysis was itself a false positive on the same mechanism, which makes it the wrong foundation to
build an irreversible stop on. `runOrchestrator.js`'s retry-stop decision
(`isFinalAttempt || noProgress`) is unchanged this round, and `draftRemediationCard`'s
`agent: "dispatch"` assignment is unchanged. A follow-up card with its own evidence could revisit
this; `_handleNeedsHumanDecision` (`runOrchestrator.js:827-832`) already halts the loop
unconditionally as a precedent hook for what a genuine early-stop would plug into.

**Verification constraint, unchanged from round 1:** this `generic`-persona session's Bash grant is
`git` only -- `npx vitest run`/`npx eslint .` require approval this session and could not be run
directly. Every new and changed assertion across `blockerReport.test.js`,
`claudeDirBashGuard.test.js`, `escalationRemediation.test.js`, and
`runOrchestrator.escalation.test.js` was traced by hand against the current source, including the

### Correction 2 -- the escalation claim, narrowed (option (b))

Round 1 claims the new `permission-grant` classification routes a card to a human "instead of
burning retry attempts". **It does not.** In `runOrchestrator.js`:

```
const isFinalAttempt = attempt >= maxAttempts;
const stopping = isFinalAttempt || noProgress;
await this._handleFailValidation(taskId, verdict, attempt, !stopping, {...});
if (stopping) await this._escalateIfGenuineBlocker(...);
```

`_escalateIfGenuineBlocker` -> `buildBlockerReport` -> `categorizeFailure` runs **only once
`stopping` is already true**. The category cannot influence the stop decision. And
`draftRemediationCard` sets `agent: "dispatch"` unconditionally for every category, so the
classification does not change routing either. It changes **report text**.

**The decision, made deliberately: option (b) -- narrow the claims, do not build the
early-stop.** The reasoning belongs in the analysis:

- The Evidence shows the denial mechanism caused **zero** of the five measured failures, so a
  first-denial early-stop would optimise a failure mode with no measured occurrences.
- The failure direction is asymmetric: a wasted retry costs attempts, but a false-positive
  early-stop **abandons recoverable work**. This card exists partly because the denial matching
  produced a false positive, which makes it the wrong foundation for an irreversible stop.
- Keeping the validated piece delivers the real value: the guard fix, where ordinary git commit
  text mentioning a protected path was being denied.

**Do not implement an early-stop on this card.** A follow-up card may revisit it with its own
evidence; note for whoever picks it up that a precedent hook exists --
`_handleNeedsHumanDecision` already halts the loop unconditionally at
`runOrchestrator.js:827-832`, before any no-progress bookkeeping.
