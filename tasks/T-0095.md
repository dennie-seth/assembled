## Context

New task from `docs/HANDOFF.md` Section 4. Every item custody transfer is
a compare-and-swap on `item_instance.version`
(`docs/design/04-data-model.md` Section 3) - the loser of a concurrent
transfer race fails outright, never merges. This is INV-2
(`docs/design/08-invariants.md` Section 1), and it is not retrofittable
once items are live - get it right here.

`ItemRepo` needs to implement the specific transfer verbs from
`docs/design/07-items-economy.md` Section 3 and
`docs/design/03-net-protocol.md` Section 3, not a single generic "move"
call:

- **`leave`** - held -> world anchor
- **`use`** - held -> world anchor, plus a side-effect unlock write if the
  anchor's tag has a rule keyed to this item's `type_id`
  (`docs/design/10-time-and-progression.md` Section 3)
- **`take`** - world anchor -> held (one-taker: first CAS win gets it)
- **`transmute`** - two held instances consumed, one new instance minted,
  net −1 (`07-items-economy.md` Section 6) - this one is not a
  single-row CAS, it's two consuming updates + one insert in one
  transaction

Death/quit are not calls into this repo from a client - they're a
server-triggered bulk "scatter all this identity's held instances to
world anchors," using the same CAS machinery as `leave`, fired from
session eviction/expiry (D-8, `07-items-economy.md` Section 3).

## Acceptance

- [ ] `ItemRepo` implements `leave`/`use`/`take`/`transmute`, each taking
      an `expected_version` and only applying if it still matches,
      incrementing `version` and `custody_depth` atomically on success
- [ ] Test: concurrent transfer attempts on the same instance - exactly
      one wins, the other observes a conflict and does not partially apply
- [ ] Test: `custody_depth` strictly increases, never decreases or resets
      (INV-5)
- [ ] Test: `transmute` consumes both input instances and mints exactly
      one new instance of the pattern's `type_id`, atomically
