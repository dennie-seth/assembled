## Context

Backlog-review gap: `03-net-protocol.md` §3's transfer verbs (`leave`,
`use`, `take`) are CAS-guarded (INV-2, `version`) but have no idempotency
story for a request whose *response* is lost — a client that retries a
`take` after a timeout currently has no way to distinguish "my first
call never landed" from "my first call landed and the network ate the
200." This card adds that.

No `transfer_id` or receipts concept exists yet in `03` or
`04-data-model.md` — this is new schema and new endpoint behavior, not a
gap-fill against an existing spec. It sits alongside `ItemRepo`'s CAS
work (T-0095).

## Story

As the server, I want each transfer request to carry a client-minted
`transfer_id` as its primary key, so that a retried request returns the
stored outcome of the original attempt instead of re-running the
compare-and-swap.

## Acceptance

- [ ] `leave`/`use`/`take` (and `transmute`) accept a client-generated
      `transfer_id` (UUID); the server persists it as the primary key of
      a receipt row alongside the transfer's outcome (success + new
      `version`, or the specific conflict)
- [ ] A repeat request with the same `transfer_id` returns the
      **stored** outcome without re-running the CAS — it must not
      attempt the mutation a second time, even if the underlying item's
      `version` has since changed for unrelated reasons
- [ ] A request with a `transfer_id` never seen before executes
      normally and records its outcome
- [ ] Receipts are retained 72h (matches the retention job in T-0125's
      sweep worker) and are not required to survive past that window
- [ ] Test: same `transfer_id` submitted twice concurrently — exactly
      one CAS attempt happens; both callers receive the same stored
      outcome
- [ ] Test: retrying after 72h (receipt expired) is treated as a fresh
      transfer, not an idempotent replay
