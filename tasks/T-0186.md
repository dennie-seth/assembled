## Context

171 validation notes recorded, 56% (96) landed as FAIL/rework rather than
PASS-first-try -- the same numbers the flow-stats self-improvement loop
already flagged automatically (see the existing auto-proposed card, real
id T-0183, "Flow health: rework rate 56% over 171 validations"). That
card's suggested direction is "read the FAIL notes for a shared root
cause and land one infra fix" -- useful for finding one grant/guard bug,
but it doesn't distinguish two very different explanations for a high
aggregate rate: the reviewer catching real defects (working as intended)
vs. cards not containing the information an implementer needed to get it
right the first time (a card-authoring problem). This card is that
distinction, not a duplicate of the auto-proposed one -- it's a sampled
investigation rather than an aggregate-trigger response.

The existing auto-proposed flow-health card (T-0183) covers the same
trigger numbers with a narrower "find one infra fix" framing; this card's
sampled classification is the broader investigation and should inform
whether that card's suggested infra fix is even the right lever to pull.

**Grounding:** `docs/design/flow-stats-self-improvement.md` §Problem
("a card that keeps failing the same lint rule for five auto-retries…
are all visible one card at a time but invisible as a trend") and
§Post-launch revision (evidence-carrying drafts, concrete card ids).
T-0183's root-cause analysis (ruff I001 pattern) is one data point this
investigation should subsume.

## Story

As the board process, I want a sampled read of ~20 reworked cards that
asks, per card, "did the rework fix a genuine defect, or did it supply
information the card should have contained the first time" -- so that
scaling decisions are made on "the reviewer is doing its job" vs. "cards
are underspecified" rather than on the raw 56% number alone.

### Other/Infra bucket: orchestrator status-drift

T-0043 and T-0072 are pure infra failures (reviewer Bash grants too narrow).
A distinct infra pattern appears as the secondary cause in T-0143, T-0145,
and T-0147: the orchestrator advances the card's `status` on `develop` after
each FAIL verdict, but the feature branch holds a now-stale copy. The diff
guard mechanically detects the mismatch and issues a FAIL, even though the
implementer never touched the status field. These FAILs are not implementer
defects and not card-authoring gaps — they are an orchestrator lifecycle bug.
They are counted in the primary classification of the card (genuine defect
for T-0143/T-0145, underspecified for T-0147) and do not migrate entries
between buckets, but they inflate the raw FAIL count without representing
either a reviewer doing its job or a card-authoring problem. If stripped
from the aggregate, the adjusted split across the 16 cards would be roughly
the same in category ratio but with fewer total FAIL events.

### Card-authoring changes warranted

The underspecified count is 6 of 16 (non-trivial). The following concrete
changes are warranted:

**1. Bare user-story sentences must not reach an implementer without planner
expansion.** T-0139, T-0140, T-0141, T-0147, and T-0170 all had the pattern
"As a user I want X." with nothing else in the body. In every case the code
was correct and the FAIL was solely the missing Acceptance section. A pre-
queue check (already planned via T-0111's planner-expansion path for
`agent: null` cards) should be enforced: any card body that contains no
`## Acceptance` section must be blocked from dispatch until the planner adds
one.

**2. The `## Acceptance` section must be machine-checked before an
implementer run starts, not only at review.** The reviewer currently FAILs
cards with no Acceptance checklist — but that costs an implementer LLM call
plus a reviewer LLM call for a failure detectable in one line of JavaScript
(`parseAcceptanceCriteria` already exists in `acceptanceCriteria.js`).
The runner should check for the presence of a parseable Acceptance checklist
as a pre-flight gate and block the run with a clear message rather than
waiting for the reviewer to surface this.

**3. Each acceptance criterion must assert observable behavior, not a static
property.** Several cards that did have Acceptance sections still generated
rework because criteria were too shallow (T-0141: the planner.md lesson
explicitly cites this as the T-0141 lesson — `.board has overflow-x: auto`
is a CSS-property check, not a behavioral assertion). Card authors should
write criteria in the form "with X happening, Y is observable" rather than
"property Z is set."

**4. The orchestrator status-drift bug should be fixed independently.** The
pattern in T-0143/T-0145/T-0147 (develop's status advancing between retries,
causing the diff guard to FAIL on stale branch copies) generated multiple
infra FAILs that have no relation to card quality. The runner should
synchronize the branch's task-card status field with develop's current value
immediately before each reviewer invocation rather than leaving it to drift.
This is a separate card from card-authoring changes, but it materially inflates
the aggregate FAIL count.
