## Context

[T-0311](T-0311) (`docs/assets/kohya-resume-behavior.md`) traced
`lora_train.train`'s `--resume` path through `accelerate.load_state` and
confirmed the optimizer/scheduler/RNG state is genuinely restored, but
found a second, separate gap: the epoch/step *display* bookkeeping
(`train_state.json`'s `current_epoch`/`current_step`, and the numbered
`-NNNNNN-state` directory suffix derived from it) is **recomputed per
invocation**, not restored, and is not a reliable cumulative counter across
a resume boundary.

Specifically (`kohya-resume-behavior.md` §5, citing
`sd-scripts/train_network.py:1467-1469`):

```
epoch_to_start = initial_step // num_update_steps_per_epoch
```

`initial_step` comes from the *previous* run's `train_state.json`
(genuinely carried forward), but `num_update_steps_per_epoch` is
recomputed fresh from `len(train_dataloader)` on **this** invocation
(`train_network.py:1385`) — so if the dataset size changes between
runs (T-0274's profile reference set was actively curated across
same-day sessions), the displayed epoch number can move in ways that
don't reflect real training progress, even though the underlying
optimizer/scheduler state carried forward correctly. T-0274 observed
this as an apparent backward jump (`current_epoch: 7` → `5` → `6`,
`ARM_PROFILE_LORA_ATTEMPT_LOG_T0274.md:46-53`).

T-0311's own doc could not settle from static reading alone whether a
changed `num_update_steps_per_epoch` is *actually* what produced that
specific 7→5/6 sequence, versus some other cause on the same code path —
confirming it needs instrumentation, which T-0311 was explicitly scoped
to not do (docs-only, no training run).

## Story

Add lightweight, per-`--resume` logging inside the `lora_train` wrapper
(`assets/src/lora/src/lora_train/train.py`) so a human or a future card can
tell, from the run log alone, whether a resumed run's cumulative position
is being tracked correctly — without re-deriving it from source after the
fact the way T-0311 had to.

1. When `find_resume_state()` selects a `-state` dir to resume from, log
   (or write to a sidecar file alongside the run's existing logs) the
   dataset size / `num_update_steps_per_epoch` this invocation computed,
   and the `current_step`/`current_epoch` values read back from the
   resumed dir's `train_state.json`.
2. Do this as a read-only observability addition — no change to
   `find_resume_state()`, resume selection, or any training default.
   (T-0311's "Do not" section forbade touching this code; this card is
   the follow-up that's now allowed to, but the change here is additive
   logging, not behavior.)
3. Document, in this card or a short note in
   `assets/src/lora/`, what the logged numbers mean and how to read them
   to confirm (or refute) that a given resume's cumulative position is
   sound.

## Acceptance

- [ ] `lora_train.train` logs, on every `--resume` invocation, at minimum:
      the resumed-from dir's `train_state.json` `current_step` and
      `current_epoch`, and this invocation's own computed
      `num_update_steps_per_epoch` (or the raw dataset length it derives
      from)
- [ ] No change to `find_resume_state()`'s selection logic, resume
      defaults, or anything that affects what gets passed to
      `sdxl_train_network.py` — verified by diff review against
      `assets/src/lora/src/lora_train/train.py`'s pre-existing behavior
- [ ] A short doc note (in this card's body or a new
      `assets/src/lora/RESUME_LOGGING.md`) explains what the logged values
      mean and how to use them to confirm cumulative position across a
      resume, referencing [T-0311](T-0311)'s findings
- [ ] Test coverage (per `.claude/rules/python.md`, test-first) for the new
      logging call — asserting it fires on a `--resume` path and does not
      fire when no resume state is found, without requiring an actual
      training run

**Edge cases:**
- [ ] First-ever run (no `-state` dir found, nothing to resume) — logging
      call must not fire and must not error
- [ ] A `-state` dir whose `train_state.json` is missing or unparseable —
      logging degrades to noting that explicitly, does not crash the
      training invocation
