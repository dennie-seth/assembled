## Context

Note on the spec citation: this lands in `04-data-model.md` §4
(Progression) — the `unlock` table lives there, not §6 (which is
Cross-References only). Confirmed against the file as currently written.

`unlock(token, variant_id, tag, expires_at)` is per-`(variant_id, tag)`
(`04` §4) — you opened *that* door in *that* Hospital, not the archetype
in general (`01-vision.md` §7). Decay is tiered, not a single duration
(`10-time-and-progression.md` §3):

| Tier | Duration | Nature |
|---|---|---|
| Tactical | minutes | not progression at all |
| Session | hours-days | cross-session convenience |
| Unique-keyed | ~1 week (T-2, open) | the only thing that accumulates |

An unlock is granted as a side effect of `use` (`03-net-protocol.md` §3)
— there is no separate unlock endpoint.

## Story

As the server, I want to persist `(token, variant_id, tag)` unlocks with
tier-appropriate decay, so that only unique-keyed unlocks meaningfully
accumulate across sessions while tactical/session unlocks lapse on their
own.

## Acceptance

- [ ] `unlock` rows are keyed `(token, variant_id, tag)` with an
      `expires_at`, written as a side effect of a successful `use`
      transfer that resolves against a lock (`03-net-protocol.md` §3)
- [ ] `expires_at` is set according to the unlock's tier (tactical /
      session / unique-keyed) rather than one fixed duration for all
      unlocks
- [ ] An expired unlock is treated as absent by every read path — no
      separate "expired but present" state leaks through
- [ ] Test: a tactical-tier unlock is unusable after its short window
      even though the row technically still exists until swept
- [ ] Test: a unique-keyed unlock persists across a session boundary
      (new lease, same identity) until its ~1-week expiry
- [ ] Note: T-1/T-2's exact durations are open tuning
      (`docs/HANDOFF.md` §6) — implement against the tier concept and a
      configurable duration per tier, not a hardcoded number
